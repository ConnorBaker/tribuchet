# The `integration` branch

This branch is upstream `main` (Mic92/tribuchet) with this fork's topic branches merged into it, one `git merge --no-ff` per topic, in the order below, each as "Merge topic '<name>'". It is what the farm builds and runs; it is not meant to go upstream as a whole. Each topic branch is its own unit and goes upstream (or not) on its own.

Each topic branch is a linear stack of commits on upstream `main`, or on the topics it depends on ("Stacked on"). A topic that depends on two or more topics sits on a merge of them, named "Merge topic '<a>' into the base of '<b>'" or "Merge topic '<a>' into <b>", so that merge's commits are part of the topic's history but not of its own change.

Base `main` commit: `1a1002096f3c1f6d7b32b3ef9822e542b095a948`

"Stacked on" names the earlier topics whose merged heads the topic's head contains, leaving out any that another of them contains; "this branch at `<sha>`" means the topic sits on that commit of this branch, and the topics after it are the ones that commit does not contain.

The `integration: describe the merged branches` commits only add or update this file and the two scripts in `maintainers/`.

## Regenerating and checking

`maintainers/integration-table.sh [<commit> [<file> | -]]` rewrites the table from the merges: order, topic, head, merge date and "Stacked on" come from history; Description and Upstream PR are kept from each topic's row, and a new topic is named on stderr to be described. It writes nothing and exits 1 when the base is not on the first-parent history; the table header is missing, renamed or repeated; a row does not have seven cells (a `|` in a description) or a row-shaped line stands outside the table; there is no merge; or a merge is an octopus or not "Merge topic '<name>'".

`maintainers/integration-status.sh [<commit>]` (no network; fetch first) reads the INTEGRATION.md committed in `<commit>` (default `HEAD`), not the work tree's, and runs on it the `integration-table.sh` committed in that same commit. A commit that also changes `integration-table.sh` is therefore checked by its own regenerator, and one that breaks it (one that just echoes its input, say) passes whatever its table says: a change to `integration-table.sh` must be reviewed itself. Any difference between the committed file and the regenerated one is printed as a diff and fails the check, as does a refusal of `integration-table.sh`; the regenerator is the one place that decides the derived columns. It then prints for each topic the local and `fork/` tips of its branch (the topic's name, or the one a "Fork branch of" line names) and whether each is UP-TO-DATE, BEHIND (n commits), REWRITTEN or MISSING. It exits 1 if anything is not up to date or the table differs.
